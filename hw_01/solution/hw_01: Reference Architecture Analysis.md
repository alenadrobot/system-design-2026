# **0. Контекст системы**

**Сформулировал, что делает система в 1-2 предложениях**

Облачное хранилище данных позволяет пользователям загружать файлы, скачивать их, редактировать, удалять и делится доступом к файлам. Также оно позволяет синхронизировать файлы между разными устройствами 

Пусть у этого облачного хранилища есть только мобильное приложение для пользователей (хочу сосредоточится не на фронте в этом дз)

**Назвал основных пользователей / акторов (кто и зачем обращается к системе)**

Авторизированный Пользователь - может загружать/скачивать/редактировать свои файлы и файлы, к которым у него есть доступ 

Неавторизированный пользователь - может просмотреть файлы, к которым ему дали доступ по публичной ссылке

Админ - настраивает тарифы (какая стоимость за сколько ГБ данных)

**Выписал ключевые сценарии использования (3-5 штук) — что система делает чаще всего**

1. Система должна предоставлять пользователю возможность загрузить файл 
2. Система должна предоставлять пользователю возможность отредактировать файл 
3. Система должна предоставлять пользователю возможность скачать файл 
4. Система должна предоставлять пользователю возможность просмотреть диревторию файлов 
5. Система должна предоставлять пользователю возможность найти файл по имени/по части имени 
6. Система должна предоставлять пользователю возможность делиться доступом к файлу с другим пользователем 
7. Система должна обеспечивать синхронизацию файлов между устройствами пользователя

**Отметил масштаб (порядок: тысячи / миллионы пользователей, объём данных, RPS) — хотя бы грубо**

Кол-во пользователей

У похожих решений кол-во пользователей измеряется миллионами (Dropbox, Яндекс диск, OneDrive), поэтому предположу, что у выбранного решения тоже миллионы пользователей (у Google Dock конечно миллиарды, но мы пока скромные :))  

Пусть будет 100 млн пользователей, которые пользуются сервисом (на бесплатном или платном тарифе)

Пусть MAU (Month active users) =  30% от всех юзеров (потому что не всем юзерам каждый меся надо заходить в хранилище) =  30% * 100 млн = 30 млн

Пусть DAU (Day active users) = 20% от MAU (потому что юзер часто не надо каждый день заходить, это не мессенджер) = 6 млн 

Если каждый пользователь проводит примерно 10 мин в приложении, то кол-во одновременно активных юзеров = 6 млн * 10 * 60 / 60 * 60 * 24 = примерно 40k пользователей

Пиковая нагрузка предположим, что 40k *2 = 80k пользователей

Объем данных 

Данные тяжелые, потому что пользователи хранят фото и видео. Пусть у одного пользователя в среднем хранится файлов на 10 GB. Тогда 100 млн * 10 GB = 1,000,000,000 GB = 1,000 PB = 1 EB. Значит порядок PB - EB

RPS 

Есть 2 вида запросов 

1) К Meta данным, чтобы получить информацию о файле, получить как файлы лежат в директории. Они небольшие, но их много. Пусть пользователь делает meta запрос раз в 5 сек (потому что с облачными хранилищами работают долго, надо открыть директорию, просмотреть файлы, подумать) Если 40k одновременно активных пользователей, то 

RPS  = 40k / 5 = 8k

RPS пиковая = 80k / 5 = 16k

2) Большие на загрузку/скачивание файлов. Эти операции делают реже, но все еще часто (вряд ли пользователь приходит посмотреть чисто мета информацию своих файлов. Кэш конечно помогает, но скорее всего пользователь хочет скачать/загрузить файл, раз уж он открыл приложение). Пусть 20% от одновременно активных юзеров загружает или скачивает файлы, значит  40k * 20% = 8k

Если средняя скорость скачивания = 5 MB/sec, то общий сетевой трафик в секунду = 8k * 5 MB/sec = 40k MB/sec = 40 GB/sec

# **Компоненты**

Основные сервисы и их ответственности (5-10 компонентов)

1. **Фронт (мобильное приложение или веб приложение или десктоп приложение)**
    1. дает пользователю интерфейс для работы с облачным хранилищем
    2. вызывает API Gateway
    3. хранит файлы локально
2. **API Gateway**
    1. направляет запросы на нужные сервисы
    2. проверяет токен пользователя
    3. Load Balancing  (в том числе Geo-based balancing)
    4. Rate Limiting
    5. логирование и мониторинг
3. **Auth Service + users DB**
    1. авторизация и аутентификация пользователей
4. **Storage Service + Object storage (S3) -** сервис по работе с файлами
    1. управление файлами (загрузка/скачивание/удаление/редактирование
    2. обработка файла при загрузке, если необходимо
5. **Metadata Service + Metadata DB (relational)** - Сервис по работе с метаданными (кто владелец, какие версии, поисковые теги)
    1. управление записью о файле (создать/редактировать/удалить)
    2. хранение структуры папок
6. **Search Service + Search Index** - сервис для поиска файлов в облачном хранилище
    1. Поиск файла по имени или по части имени
    2. Ускорение поиска, обновление  **Search Index** 
7. **Sync Service** - сервис для синхронизации файлов между устройствами
    1. отслеживание изменений
    2. отправка изменений на другие устройства
    3. хранение версий
    4. решение конфликтов между двумя версиями
    5. управление оффлайн измененными файлами
8. **Permission Service + Permission DB** - сервис для управления доступом к файлам 
    1. выдача разных прав на управление файлом (только чтение, чтение и редактирование, удаление)
    2. проверка прав пользователя на файл
    3. выдача доступа другому пользователю
    4. создание публичной ссылки для доступа неавторизованных пользователей
9. **Billing Service +Billing DB** - сервис тарификации
    1. упарвление тарифом пользователя (переход с бесплатного на платный, переход на другой тариф, отмена тарифа) 
    2. проверка, есть ли место у пользователя в рамках выбранного тарифа 
    3. списание денег за пользование хранилищем
10. **CDN** - сеть серверов, чтобы хранить данные ближе к пользователю и отдавать их быстрее. Сторонее решение (например, Amazon CloudFront  или CloudFlare) 
11. **Event bus(kafka)** брокер сообщений. Используем для вынесения не критичных операция ассинхронно. Например, после загрузки файла - чтобы проверить на вирусы, обновить информацию в других сервисах, обработать файл (если необходимо), подготовить иконки-превью
12. **Thumbnail Service**  - сервис для создания превью файлов

# **Потоки данных**

3-5 ключевых сценариев

1. Пользователь загрузил новый файл
    1. **пользователь** выбрал файл в приложении
    2. Фронт передает запрос на **API Gateway** POST files/upload (хочу загрузить файл)
    3. **API Gateway** через **Auth Service** проверяет токен пользователя
    4. **Api Gateway** вызывает **Storage Service**
    5. **Storage Service** через **Billing Service** проверяет, что пользователь может загрузить файл (есть место, тариф оплачен)
    6. **Storage Service** создает signed URL, и через **Gateway** возвращает ее в приложение
    7. **приложение** через signed URL загружает файл в **Object Storage** (юзер не может ничего делать, пока файл загружается. И не закрывает приложение)
    8. **приложение** отображает пользователю “ваш файл загружен, на других устройствах появится после обработки”. Юзер может что-то делать дальше в приложении, остальная обработка файла идет ассинхронно
    9. **Object Storage** передает **Storage Service**, что файл загружен
    10. **Storage Service** публикует event в event bus, что загружен новый файл. Туда кладет метаданные
    11. **Metadata Servise** видит event и создает запись с метаданными
    12. **Sync Service** видит event и оповещает другие устройства, что появился новый файл
    13. **Thumbnail Service**  ****видит event и создает превью файла. Он сохраняет превью в **Object Storage** и вызывает **Metadata Service,** чтобы сохранить путь к превью в **Metadata DB**
    14. **Search Service** видит event и редактирует индексы для поиска
    15. **Permission Service** видит event и добавляет все права пользователю, загрузившему файл
    16. **Billing Service** видит event и обновляет кол-во свободного места для пользователя
2. Пользователь просматривает директории файлов 
    1. пользователь открыл приложение
    2. Фронт передает запрос на **API Gateway**   GET folders/{folder_id}/files (хочу узнать, какие файлы лежат в папке {folder_id})
    3. **API Gateway** через **Auth Service** проверяет токен пользователя
    4. **API Gateway** вызывает **Metadata Service**
    5. **Metadata Service** находит все файлы, которые лежат в {folder_id}
    6. **Metadata Service** запрашивает у **Permission Service,** к каким файлам пользователь имеет доступ
    7. **Metadata Service** отдает **Api Gateway** инфу о файлах, которые лежат в {folder_id} и к которым пользователь имеет доступ
    8. Приложение отображает полученные файлы
3. Пользователь ищет файл
    1. пользователь вбил в приложении название файла
    2. Фронт передает запрос на **API Gateway** GET files/search?query ={name} (хочу найти файл name)
    3. **API Gateway** через **Auth Service** проверяет токен пользователя
    4. **API Gateway** вызывает **Search Service** и передает query и id пользователя (чтобы только файлы этого пользователя найти)
    5. **Search Service** находит все подходящие файлы с помощью индексов
    6. **Search Service** запрашивает информацию о файлах у **Metadata Service** 
    7. **Metadata Service** запрашивает у **Permission Service,** к каким файлам пользователь имеет доступ
    8. **Metadata Service** отдает **Search Service** инфу о файлах, к которым пользователь имеет доступ
    9. **Search Service** сортирует полученные результаты и отдает информацию **API Gateway**
    10. **API Gateway** отдает ответ **приложению**, **приложение** отображает найденные файлы пользователю
4. Пользователь скачивает файл
    1. **пользователь** выбрал файл в приложении
    2. Фронт передает запрос на **API Gateway** GET files/{file_id}/download (хочу скачать файл)
    3. **API Gateway** через **Auth Service** проверяет токен пользователя
    4. **Api Gateway** вызывает **Storage Service**
    5. **Storage Service** запрашивает у **Metadata Service, где в Object Storage** лежит этот файл
    6. **Metadata Service** запрашивает у **Permission Service**, имеет ли пользователь доступ на чтение к этому файлу
    7. **Storage Service** создает signed CDN URL, и через **Gateway** возвращает ее в приложение
    8. **приложение** через signed CDN URL скачивает файл из **CDN.** Если файла в **CDN** нет, то **CDN** скачивает файл из **Object Storage** и кэширует у себя
    9. **если скачивание успешно, то приложение** отображает пользователю “ваш файл добавлен на устройство” и сохраняет файл в кэш
5. Пользователь дает доступ на чтение или редактирование файла другому пользователю
    1. **пользователь** добавляет права на чтение/редактирование файла для пользователя user
    2. Фронт передает запрос на **API Gateway** POST files/{file_id}/permissions (хочу дать доступ к файлу fileId пользователю userId) c параметрами
        1. user = {user_id}
        2. permission = “read” или ”edit”
    3. **API Gateway** через **Auth Service** проверяет токен пользователя
    4. **Api Gateway** вызывает **Permission Service** 
    5. **Permission Service**
        1. проверяет, что пользователь может выдавать доступ
        2. добавляет, что у пользователя userId есть доступ к чтению и/или редактированию файла file_id (создаёт запись в Permission DB)
    6. **Permission Service** публикует event в event bus, что у пользователя user есть доступ к чтению и/или редактированию файла file_id
    7. **Permission Service** отдает успешный ответ через **Gateway в приложение**
    8. **Sync Service** видит event и добавляет запись, что новый файл стал доступен
    9. если приложение user было открыто, то с помощью webhook оно получает информацию, что доступен новый файл
6. Пользователь отредактировал файл
    1. **пользователь** отредактировал файл в приложении
    2. приложение вычисляет изменение в файле
    3. Фронт передает запрос на **API Gateway** PATCH files/{file_id} (хочу отредактировать файл) c параметрами
        1. current_version = {current_version}
        2. diff = “…”
    4. **API Gateway** через **Auth Service** проверяет токен пользователя
    5. **API Gateway** вызывает **Storage Service**
    6. **Storage Service** запрашивает у **Permission Service**, имеет ли пользователь доступ на редактирования у этого файла
    7. **Storage Service** создает копию файла и применяет к ней дифф. Это новая версия файла (старая пока не удаляется)
    8. **Storage Service** публикует event в event bus, что появилась новая версия файла
    9. **Metadata Servise** видит event и обновляет запись с метаданными
    10. **Sync Service** видит event и обновляет у себя запись, что файл был изменен. И оповещает устройства, на которых этот файл скачан, если там приложение сейчас открыто (иначе новая версия будет скачана при открытии приложения) 
    11. **Thumbnail Service**  ****видит event и обновляет превью файла (если нужно)
    12. **Search Service** видит event и редактирует индексы для поиска
    13. **Permission Service** видит event и добавляет все права пользователю на новый файл

# **Проблемы и решения**

Какие проблемы решает каждый компонент

Каждый компонент может решать бизнес и/или технические проблемы. Указала примеры и тех, и тех 

1. **Фронт** 
    1. Как предоставить понятный интерфейс, чтобы пользователь легко мог загружать, просматривать, редактировать свои файлы, давать доступ к файлам, работать с чужими файлами, etc
    2. Как отображать моменты загрузки или синхронизации, чтобы пользователь в этот момент не закрыл приложение и не сломал все :) 
2. **API Gateway** 
    1. Как скрыть внутреннюю архитектуру от клиента и дать ему единую точку доступа в систему. Чтобы не хранить на клиенте пути до каждого сервиса. Потому что если они поменяются или если несколько экземпляров одного сервиса, то надо на клиенте решать, к какому посылать запросы. Это лишнее усложнение 
    2. Как ограничить кол-во запросов, если сервисы не справляются. И как потом отработать эти запросы или убедить пользователя повторить действие (rate limiting) 
    3. Как маршрутизировать запросы, если запущено несколько экземпляров одного сервиса. Или как запустить новый экземпляр, если один сервис не справляется или упал 
3. **Auth Service**
    1. Как безопасно авторизовать и аутентифицировать пользователя. Можно использовать access и refresh токен, чтобы понимать, что пользователь правда тот, за кого себя выдает 
    2. Как обновлять access refresh токены 
4. **Storage Service** 
    1. Как эффективно загружать и скачивать  большие файлы с приложения в object storage при условии, что много пользователей могут загружать/скачивать много файлов одновременно 
    2. Как дать object storage допустимую нагрузку, если много одновременных загрузок файлов 
    3. Как безопасно выдавать временный доступ к объектам через signed URLs
    4. Как эффективно редактировать файл (чтобы не передавать лишнюю информацию по сети) 
5.**Object storage** 
    1. Как хранить много файлов (желательно дешево) 
    2. Как хранить тяжелые файлы (желательно дешево) 
    3. Как масштабироваться, если память начинает заканчиваться 
6. **Metadata Service** 
    1. Как быстро отдавать информацию о файлах 
    2. Как хранить структуру папок
    3. Как хранить версии файлов 
    4. Как быстро редактировать информацию о файлах, чтобы не перезагружать весь файл 
7. **Search Service** 
    1. Как быстро искать файлы, когда хранятся огромные объемы файлов 
    2. Как дать пользователю возможность искать файлы разными способами (по названию, по части названия) 
    3. Как убрать тяжелый запросы на поиск файлов из Metadata DB 
    4. Как обновлять search index и поддерживать его актуальным 
8. **Sync Service**
    1. Пользователь обновил файл на одно устройстве. Как обновить на других? 
    2. Два пользователя обновляют файл одновременно. Что делать? 
    3. Пользователь обновил файл в режиме оффлайн. Как передать изменения на бэкенд? 
9. **Permission service** 
    1. Как выдавать разные права разным пользователям к разным файлам 
    2. Когда и как убирать доступ какого-то пользователя, чтобы не было утечек данных
    3. Как выдавать доступ неавторизованным пользователям 
10. **Billing service** 
    1. Как проверять при загрузке файла, что пользователь оплатил за сервис и у него достаточно места?
    2. Как списывать оплату с пользователя? 
    3. Что делать, если пользователь не оплачивает, а его тариф закончился, а у него все еще есть файлы? 
11. **CDN**
    1. Проблема - как быстро отдавать пользователям файл, если пользователи находятся в географически разных точках (уменьшить latency) 
    2. Как снизить нагрузку на object storage 
12. **Event bus** 
    1. Как уменьшить кол-во синхронных операций при загрузке файла? По сути, как ускорить загрузку файла для пользователя . Для этого операции над файлом с некритичного пути можно сделать асинхронно. И мы разгружаем Storage Service - ему нужно только загрузить файл, а дальше обработку файла, обновление в связи с добавлением нового файла можно сделать асинхронно 
    2. Как разделить сервисы и уменьшить связность сервисов 
13. **Thumbnail Service**
    1. Как быстро показывать превью файлов, чтобы не скачивать при этом весь файл? 
    2. Как генерировать превью для разных типов файлов (изображение, видео, текст)
